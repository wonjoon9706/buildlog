# BuildLog 개발 계획

## 1. 문서 목적

이 문서는 `spec.md`에 정의된 BuildLog 첫 번째 버전을 어떤 순서로 개발할지 정리한 실행 계획입니다.

각 Phase는 다음 Phase를 시작하기 전에 확인해야 할 결과물을 만듭니다. 기능을 한꺼번에 만든 뒤 마지막에 확인하지 않고, 작은 단위로 만들고 바로 검증하는 방식을 사용합니다.

## 2. 개발 순서 한눈에 보기

```text
Phase 0  개발 기준 고정
   ↓
Phase 1  프로젝트 기본 구조와 실행 환경
   ↓
Phase 2  데이터베이스와 공통 백엔드 기반
   ↓
Phase 3  회원 가입·로그인·권한 보호
   ↓
Phase 4  공통 화면과 메뉴
   ↓
Phase 5  학습 기록
   ↓
Phase 6  할 일
   ↓
Phase 7  오류 기록
   ↓
Phase 8  검색과 필터
   ↓
Phase 9  대시보드
   ↓
Phase 10 반응형 화면과 공통 사용 경험
   ↓
Phase 11 전체 연결·보안·회귀 점검
   ↓
Phase 12 배포와 첫 버전 공개
```

이 순서를 사용하는 이유는 다음과 같습니다.

- 로그인과 사용자 구분을 먼저 만들어야 이후의 모든 기록을 안전하게 소유자와 연결할 수 있습니다.
- 학습 기록, 할 일, 오류 기록이 있어야 검색과 대시보드를 실제 데이터로 만들 수 있습니다.
- 모든 기능이 연결된 뒤 휴대폰 화면과 전체 사용 흐름을 한 번에 다듬는 편이 누락을 찾기 쉽습니다.
- 배포는 기능과 보안 확인이 끝난 뒤 진행합니다.

## 3. 모든 Phase에 적용할 작업 원칙

- 한 Phase에서는 정해진 범위만 구현합니다.
- 프론트엔드 입력 검사만 믿지 않고 백엔드에서도 같은 조건을 확인합니다.
- 모든 개인 데이터 요청에서 현재 로그인한 사용자가 작성자인지 확인합니다.
- 성공, 잘못된 입력, 처리 실패를 각각 구분해 사용자에게 쉬운 안내를 보여줍니다.
- 새 기능을 만들 때 정상 동작뿐 아니라 실패와 권한 차단도 함께 확인합니다.
- 기능이 끝날 때마다 자동 확인과 직접 화면 확인을 모두 수행합니다.
- `spec.md`에 없는 기능은 편의상 추가하지 않습니다.
- 비밀값은 `.env`에 두고, 실제 비밀값이 없는 항목 예시는 `.env.example`로 공유합니다.

**상태: 완료 (2026-10-26)**
완료 점검 결과: [`phase-0-checklist.md`](phase-0-checklist.md)

### 목표

개발 중 요구사항이 흔들리지 않도록 기준 문서와 첫 버전의 범위를 확인합니다.

### 진행 단계

1. `mvp.md`, `PRD.md`, `spec.md`의 역할을 확인합니다.
2. 실제 기능 동작은 `spec.md`를 최종 기준으로 삼습니다.
3. 첫 버전에서 만들 기능과 만들지 않을 기능을 작업 목록으로 나눕니다.
4. `spec.md`의 전체 완료 확인표를 이후 최종 점검표로 사용합니다.
5. 기능 이름과 화면 이름을 문서와 동일하게 맞춥니다.

### 결과물

- 확정된 개발 범위
- Phase별 작업 목록
- 첫 버전 제외 기능 목록

### 완료 조건

- 회원 가입·로그인, 대시보드, 학습 기록, 할 일, 오류 기록, 검색·필터가 구현 대상에 포함되어 있습니다.
- 공개·공유, 댓글·좋아요, 신고 등 제외 기능이 구현 작업에 들어가 있지 않습니다.
- 개발 중 판단이 필요할 때 어떤 문서를 기준으로 볼지 정해져 있습니다.

## 5. Phase 1 — 프로젝트 기본 구조와 실행 환경

**상태: 완료 — SQLite3 기준 (2026-10-26)**
완료 점검 결과: [`phase-1-checklist.md`](phase-1-checklist.md)

### 목표

프론트엔드, 백엔드와 데이터베이스를 각각 실행하고 서로 연결할 수 있는 최소 기반을 만듭니다.

이 프로젝트는 React 프론트엔드와 FastAPI 백엔드를 분리합니다. 현재 데이터베이스는 프로젝트 내부 SQLite3를 사용하고, 자동 테스트는 실제 개발 데이터와 분리된 메모리 SQLite3에서 실행합니다. Supabase 연동은 관련 수업 이후 별도 단계에서 검토합니다.

### 진행 단계

#### 프론트엔드

1. `frontend` 폴더에 React 프로젝트를 준비합니다.
2. 개발용 실행 명령과 기본 화면을 준비합니다.
3. 페이지 이동을 위한 기본 구조를 만듭니다.
4. 백엔드 주소를 환경 설정으로 읽을 수 있게 준비합니다.

#### 백엔드

1. `backend` 폴더에 FastAPI 프로젝트를 준비합니다.
2. 서버가 실행 중인지 확인할 수 있는 간단한 상태 확인 기능을 만듭니다.
3. 환경 설정을 읽는 공통 구조를 만듭니다.
4. 프론트엔드 요청을 받을 수 있도록 개발 환경 연결을 설정합니다.
5. 사용자에게 보여줄 오류와 서버 내부 오류를 구분할 기본 처리 방식을 만듭니다.

#### 데이터베이스

1. 개발용 SQLite3 데이터베이스 주소를 환경 설정으로 분리합니다.
2. 테스트용 메모리 SQLite3 연결 설정을 별도로 준비합니다.
3. 개발과 테스트 데이터베이스가 서로 섞이지 않게 합니다.
4. 백엔드가 개발용 SQLite3 데이터베이스에 연결되는지 확인합니다.
5. 자동 테스트가 개발 데이터에 접근하지 않는지 확인합니다.
6. 데이터 구조 변경 이력을 순서대로 적용할 수 있는 방식을 준비합니다.

#### 테스트 기반

1. 백엔드 자동 테스트가 별도의 SQLite3 데이터베이스를 만들고 사용할 수 있게 합니다.
2. 테스트가 끝나면 테스트 데이터가 다음 실행에 남지 않게 합니다.
3. 별도의 외부 데이터베이스 정보 없이 자동 테스트를 실행할 수 있게 합니다.
4. 테스트 중에는 개발용 SQLite3 파일에 연결하지 못하도록 분리합니다.

#### 공통 설정

1. `.env`에는 실제 연결 정보와 비밀값만 둡니다.
2. `.env.example`에는 항목 이름과 비밀값이 없는 예시만 기록합니다.
3. 실행 방법과 필요한 환경 설정 항목을 문서화합니다.

### 확인 방법

- 프론트엔드 기본 화면이 열리는지 확인합니다.
- 백엔드 상태 확인 요청이 정상 응답하는지 확인합니다.
- 백엔드가 개발용 SQLite3 데이터베이스에 연결되는지 확인합니다.
- 백엔드 자동 테스트가 메모리 SQLite3를 사용하고 개발 데이터에 영향을 주지 않는지 확인합니다.
- 프론트엔드에서 백엔드로 요청을 보낼 수 있는지 확인합니다.
- `.env`가 기록 대상에서 제외되고 `.env.example`은 기록할 수 있는지 확인합니다.

### 완료 조건

- 세 영역을 각각 실행할 수 있습니다.
- 프론트엔드 → FastAPI → SQLite3 연결 경로가 준비되어 있습니다.
- 자동 테스트는 메모리 SQLite3만 사용하는 별도 경로로 실행됩니다.
- 비밀값이 코드나 문서에 들어가 있지 않습니다.

## 6. Phase 2 — 데이터베이스와 공통 백엔드 기반

**상태: 완료 — SQLite3 기준 (2026-10-26)**
완료 점검 결과: [`phase-2-checklist.md`](phase-2-checklist.md)

### 목표

사용자와 세 종류의 기록을 저장할 구조를 만들고, 이후 모든 기능에서 사용할 공통 규칙을 준비합니다.

개발용 SQLite3와 테스트용 메모리 SQLite3에서 같은 기능이 동작하도록 구성합니다.

### 진행 단계

#### 데이터 구조

1. 사용자 정보를 저장할 구조를 만듭니다.
   - 사용자 번호
   - 이메일
   - 안전하게 변환된 비밀번호
   - 가입일
2. 학습 기록 구조를 만듭니다.
   - 제목, 내용, 공부한 날짜, 태그
   - 작성일, 수정일, 작성한 사용자
3. 할 일 구조를 만듭니다.
   - 내용, 선택 가능한 마감일, 완료 여부
   - 작성일, 수정일, 작성한 사용자
4. 오류 기록 구조를 만듭니다.
   - 제목, 오류 메시지, 발생 상황, 해결 여부, 해결 방법, 태그
   - 작성일, 수정일, 작성한 사용자
5. 이메일 중복을 막을 수 있게 구성합니다.
6. 사용자와 각 기록의 연결이 끊어지지 않도록 관계를 설정합니다.
7. 검색과 정렬에 자주 사용할 사용자, 날짜, 상태 정보를 빠르게 찾을 수 있게 준비합니다.
8. 개발용과 테스트용 SQLite3에서 공통으로 사용할 수 있는 데이터 형식과 기본값을 사용합니다.
9. SQLite3 외래 키 검사를 활성화합니다.

#### 공통 입력 검사

1. 이메일 형식과 비밀번호 8자 이상 조건을 준비합니다.
2. 학습 기록과 오류 기록에 필요한 제목 100자, 내용 20,000자 조건을 공통으로 적용할 수 있게 준비합니다.
3. 태그 최대 5개, 태그당 20자 조건을 준비합니다.
4. 페이지당 20개를 요청하는 목록 규칙을 준비합니다.

#### 공통 응답과 권한

1. 성공 결과의 기본 형태를 정합니다.
2. 잘못된 입력, 로그인 필요, 접근 불가, 찾을 수 없음, 서버 실패를 구분합니다.
3. 모든 기록 조회·수정·삭제에서 작성자 확인을 빠뜨리지 않도록 공통 방식을 준비합니다.

#### 테스트 데이터베이스

1. 각 자동 테스트는 깨끗한 SQLite3 데이터베이스에서 시작합니다.
2. 개발용 SQLite3에 적용할 데이터 구조를 메모리 SQLite3 테스트에도 적용합니다.
3. 저장, 조회, 수정, 삭제, 입력 검사와 권한 확인 테스트를 SQLite3에서 실행합니다.
4. 테스트가 실제 개발용 SQLite3 파일을 변경하지 않는지 확인합니다.

### 확인 방법

- 데이터 구조를 빈 SQLite3 데이터베이스에 처음부터 적용할 수 있는지 확인합니다.
- 같은 이메일을 두 번 저장할 수 없는지 확인합니다.
- 각 기록이 반드시 한 사용자와 연결되는지 확인합니다.
- 선택 사항인 할 일 마감일, 해결 방법과 태그 없이도 허용되는 경우를 저장할 수 있는지 확인합니다.
- 입력 제한을 넘는 값이 거절되는지 확인합니다.
- 자동 테스트 실행 중 개발용 SQLite3 데이터가 생성·변경·삭제되지 않는지 확인합니다.

### 완료 조건

- 사용자와 세 종류의 기록을 저장할 준비가 끝났습니다.
- 공통 입력 검사와 권한 확인 방식을 이후 기능에서 재사용할 수 있습니다.
- 데이터 구조를 다시 만들거나 변경할 수 있는 이력이 준비되어 있습니다.
- 같은 핵심 데이터 동작이 개발용과 테스트용 SQLite3에서 일치합니다.

## 7. Phase 3 — 회원 가입·로그인·권한 보호

**상태: 완료 (2026-10-26)**
완료 점검 결과: [`phase-3-checklist.md`](phase-3-checklist.md)

### 목표

사용자가 안전하게 계정을 만들고 7일 동안 로그인 상태를 유지하며, 본인의 기록에만 접근하게 합니다.

계정과 로그인은 FastAPI가 직접 처리하고 사용자와 로그인 세션은 SQLite3에 저장합니다.

### 진행 단계

#### 백엔드

1. 회원 가입 기능을 만듭니다.
2. 이메일 형식과 비밀번호 8자 이상을 검사합니다.
3. 이미 사용 중인 이메일을 거절합니다.
4. 비밀번호 원문을 안전하게 변환하여 저장합니다.
5. 가입 성공과 동시에 로그인 상태를 만듭니다.
6. 로그인 기능을 만듭니다.
7. 로그인 상태가 로그인한 기기에서 7일 동안 유지되게 합니다.
8. 로그아웃 기능을 만듭니다.
9. 현재 로그인한 사용자를 확인하는 기능을 만듭니다.
10. 로그인하지 않은 요청을 개인 기능에서 차단합니다.

#### 프론트엔드

1. 회원 가입 화면을 만듭니다.
2. 로그인 화면을 만듭니다.
3. 이메일과 비밀번호 입력 오류를 화면에서 안내합니다.
4. 가입 성공 후 별도 로그인 없이 대시보드로 이동시킵니다.
5. 로그인 성공 후 대시보드로 이동시킵니다.
6. 로그아웃 버튼과 동작을 연결합니다.
7. 로그인하지 않은 사용자가 개인 화면을 열면 로그인 화면으로 안내합니다.

### 확인 방법

- 처음 사용하는 이메일로 가입할 수 있는지 확인합니다.
- 가입 직후 자동 로그인되고 대시보드로 이동하는지 확인합니다.
- 중복 이메일, 잘못된 이메일과 8자 미만 비밀번호가 거절되는지 확인합니다.
- 저장된 비밀번호가 원문이 아닌지 확인합니다.
- 올바른 정보와 잘못된 정보로 각각 로그인해 봅니다.
- 로그아웃 후 개인 화면에 접근할 수 없는지 확인합니다.
- 두 계정으로 서로의 개인 영역에 접근할 수 없는지 확인합니다.
- 로그인 상태가 새로고침 뒤에도 유지되는지 확인합니다.

### 완료 조건

- 회원 가입, 자동 로그인, 일반 로그인과 로그아웃이 모두 동작합니다.
- 개인 화면에 로그인 보호가 적용되어 있습니다.
- 다른 사용자의 데이터에 접근할 수 없습니다.

## 8. Phase 4 — 공통 화면과 메뉴

### 목표

모든 기능이 같은 방식으로 보이고 이동할 수 있는 화면 뼈대를 만듭니다.

### 진행 단계

1. 밝은 색을 기본으로 한 공통 화면을 만듭니다.
2. 파란색 계열의 대표 색상을 적용합니다.
3. 사용 중인 기기의 기본 글꼴을 적용합니다.
4. 글자로 된 `BuildLog` 로고를 배치합니다.
5. `홈`, `학습 기록`, `할 일`, `오류 기록` 메뉴를 만듭니다.
6. 컴퓨터 화면에는 위쪽 메뉴를 배치합니다.
7. 휴대폰 화면에는 메뉴 버튼을 준비합니다.
8. 공통 입력칸, 버튼, 목록, 안내 문구와 삭제 확인창의 기본 모습을 만듭니다.
9. 불러오는 중, 내용 없음, 실패 상태의 공통 화면을 준비합니다.

### 확인 방법

- 모든 메뉴가 올바른 빈 화면으로 이동하는지 확인합니다.
- 현재 위치를 사용자가 이해할 수 있는지 확인합니다.
- 저장·취소·삭제 버튼이 서로 구분되는지 확인합니다.
- 컴퓨터와 휴대폰 크기에서 메뉴를 사용할 수 있는지 확인합니다.

### 완료 조건

- 모든 주요 화면으로 이동할 수 있는 공통 뼈대가 있습니다.
- 이후 기능이 같은 버튼과 안내 방식을 재사용할 수 있습니다.

## 9. Phase 5 — 학습 기록

### 목표

학습 기록의 작성, 목록, 상세 보기, 수정과 삭제를 완성합니다.

### 진행 단계

#### 백엔드

1. 학습 기록 작성 기능을 만듭니다.
2. 제목·내용·공부한 날짜를 필수로 검사합니다.
3. 제목 100자, 내용 20,000자를 검사합니다.
4. 태그 최대 5개와 태그당 20자를 검사합니다.
5. 로그인한 사용자를 작성자로 자동 연결합니다.
6. 본인의 학습 기록만 가져오는 목록 기능을 만듭니다.
7. 공부한 날짜가 최신인 순서로 20개씩 가져옵니다.
8. 본인의 학습 기록 하나를 가져오는 상세 기능을 만듭니다.
9. 작성자만 수정하고 삭제할 수 있게 합니다.
10. 작성일과 수정일을 올바르게 저장합니다.

#### 프론트엔드

1. 학습 기록 목록 화면을 만듭니다.
2. 학습 기록 작성·수정 공용 화면을 만듭니다.
3. 제목, 내용, 공부한 날짜와 태그 입력을 만듭니다.
4. 태그 입력 후 `Enter`를 누르면 추가되게 합니다.
5. 태그 5개 또는 20자 제한을 화면에서도 안내합니다.
6. 학습 기록 상세 화면을 만듭니다.
7. 제목, 목록, 링크와 코드 블록을 포함한 마크다운을 읽기 좋은 모습으로 표시합니다.
8. 저장 성공과 실패를 안내합니다.
9. 삭제 전 확인창을 보여주고, 확인한 경우에만 삭제합니다.

### 확인 방법

- 정상 입력으로 작성·조회·수정·삭제를 순서대로 실행합니다.
- 필수값 누락과 각 길이 제한 초과를 확인합니다.
- 태그 추가 방식, 최대 개수와 글자 수를 확인합니다.
- 마크다운 제목, 목록, 링크와 코드 블록 표시를 확인합니다.
- 21개 이상의 기록을 만들어 20개 단위 목록을 확인합니다.
- 공부한 날짜 최신순 정렬을 확인합니다.
- 삭제 취소와 삭제 확인을 각각 시험합니다.
- 다른 사용자가 조회·수정·삭제할 수 없는지 확인합니다.

### 완료 조건

- 학습 기록의 모든 작성·조회·수정·삭제 동작이 완성되었습니다.
- 입력 제한, 정렬, 20개 단위 목록과 마크다운 표시가 동작합니다.
- 작성자 외에는 기록에 접근할 수 없습니다.

## 10. Phase 6 — 할 일

### 목표

할 일의 작성, 조회, 수정, 삭제와 완료 상태 변경을 완성합니다.

### 진행 단계

#### 백엔드

1. 할 일 작성 기능을 만듭니다.
2. 할 일 내용은 필수, 마감일은 선택으로 처리합니다.
3. 새 할 일을 미완료 상태로 저장합니다.
4. 미완료와 완료한 할 일 목록을 본인 데이터로만 제공합니다.
5. 미완료 항목은 가까운 마감일 순서로 정렬합니다.
6. 마감일이 없는 미완료 항목은 마감일이 있는 항목 다음에 둡니다.
7. 완료 항목은 최근 수정한 순서로 정렬합니다.
8. 목록을 한 번에 20개씩 제공합니다.
9. 완료 여부를 양방향으로 변경하는 기능을 만듭니다.
10. 작성자만 수정하고 삭제할 수 있게 합니다.

#### 프론트엔드

1. 할 일 목록과 추가 입력 영역을 만듭니다.
2. 마감일을 비워도 저장할 수 있게 합니다.
3. 미완료와 완료 영역을 나누어 모두 보여줍니다.
4. 체크 상자로 완료와 미완료를 바꿉니다.
5. 미완료만 보는 조건을 제공합니다.
6. 할 일 내용과 마감일을 수정할 수 있게 합니다.
7. 삭제 전 확인창과 성공·실패 안내를 연결합니다.

### 확인 방법

- 마감일이 있는 할 일과 없는 할 일을 각각 추가합니다.
- 새 할 일이 미완료로 저장되는지 확인합니다.
- 마감일 정렬과 마감일 없는 항목의 위치를 확인합니다.
- 완료 체크 후 영역이 바뀌고 새로고침 후에도 유지되는지 확인합니다.
- 완료 항목을 다시 미완료로 되돌릴 수 있는지 확인합니다.
- 미완료만 보기와 20개 단위 목록을 확인합니다.
- 수정, 삭제 취소와 삭제 확인을 시험합니다.
- 다른 사용자가 접근하거나 상태를 바꿀 수 없는지 확인합니다.

### 완료 조건

- 할 일의 모든 작성·조회·수정·삭제 동작이 완성되었습니다.
- 완료 상태, 두 영역, 정렬, 필터와 20개 단위 목록이 동작합니다.
- 작성자 외에는 할 일을 보거나 바꿀 수 없습니다.

## 11. Phase 7 — 오류 기록

### 목표

미해결 오류를 먼저 저장하고, 나중에 해결 방법과 해결 상태를 추가할 수 있게 합니다.

### 진행 단계

#### 백엔드

1. 오류 기록 작성 기능을 만듭니다.
2. 제목·오류 메시지·발생 상황을 필수로 검사합니다.
3. 제목 100자와 나머지 내용 각각 20,000자를 검사합니다.
4. 태그 최대 5개와 태그당 20자를 검사합니다.
5. 미해결 오류는 해결 방법 없이 저장할 수 있게 합니다.
6. 해결됨 상태는 해결 방법이 있을 때만 저장되게 합니다.
7. 본인의 오류 기록만 최근 수정한 순서로 20개씩 제공합니다.
8. 본인의 오류 기록 상세, 수정과 삭제 기능을 만듭니다.
9. 미해결 기록만 가져오는 조건을 만듭니다.

#### 프론트엔드

1. 오류 기록 목록 화면을 만듭니다.
2. 오류 기록 작성·수정 공용 화면을 만듭니다.
3. 제목, 오류 메시지, 발생 상황, 해결 여부, 해결 방법과 태그 입력을 만듭니다.
4. 태그를 `Enter`로 추가하고 제한을 안내합니다.
5. 미해결 상태에서는 해결 방법 없이 저장할 수 있게 합니다.
6. 해결 방법 없이 해결됨을 선택하면 입력 안내를 보여줍니다.
7. 오류 기록 상세 화면을 만듭니다.
8. 미해결만 보는 조건을 제공합니다.
9. 삭제 전 확인창과 성공·실패 안내를 연결합니다.

### 확인 방법

- 해결 방법 없이 미해결 오류를 저장합니다.
- 해결 방법 없이 해결됨으로 저장할 수 없는지 확인합니다.
- 미해결 기록에 해결 방법을 추가해 해결됨으로 바꿉니다.
- 필수값과 모든 길이·태그 제한을 확인합니다.
- 최근 수정순과 20개 단위 목록을 확인합니다.
- 미해결만 보기, 수정, 삭제 취소와 삭제 확인을 시험합니다.
- 다른 사용자가 기록을 보거나 바꿀 수 없는지 확인합니다.

### 완료 조건

- 오류 기록의 모든 작성·조회·수정·삭제 동작이 완성되었습니다.
- 미해결에서 해결됨으로 바꾸는 흐름과 해결 방법 필수 조건이 동작합니다.
- 정렬, 필터와 20개 단위 목록이 동작합니다.

## 12. Phase 8 — 검색과 필터

### 목표

학습 기록과 오류 기록을 단어, 태그와 기간으로 다시 찾고 여러 조건을 함께 사용할 수 있게 합니다.

### 진행 단계

#### 백엔드

1. 학습 기록의 제목과 내용을 검색합니다.
2. 오류 기록의 제목, 오류 메시지, 발생 상황과 해결 방법을 검색합니다.
3. 영문 대문자와 소문자를 구분하지 않습니다.
4. 학습 기록과 오류 기록을 태그로 찾습니다.
5. 시작일과 종료일을 받는 기간 필터를 만듭니다.
6. 학습 기록은 공부한 날짜를 기준으로 찾습니다.
7. 오류 기록은 작성일을 기준으로 찾습니다.
8. 오류의 미해결 상태 조건과 할 일의 미완료 상태 조건을 연결합니다.
9. 검색어, 태그, 날짜와 상태를 함께 사용하면 모든 조건에 맞는 기록만 제공합니다.
10. 모든 결과에 현재 로그인한 사용자의 조건을 항상 적용합니다.

#### 프론트엔드

1. 학습 기록과 오류 기록 목록에 각각 검색창을 만듭니다.
2. 태그 선택 기능을 만듭니다.
3. 시작일과 종료일 입력을 만듭니다.
4. 오류에는 미해결, 할 일에는 미완료 조건을 연결합니다.
5. 여러 조건을 동시에 선택하고 해제할 수 있게 합니다.
6. 검색 결과가 없을 때와 처리에 실패했을 때를 구분해 보여줍니다.

### 확인 방법

- 제목에만 있는 단어와 내용에만 있는 단어를 각각 검색합니다.
- 영문 대문자와 소문자를 바꾸어 같은 결과가 나오는지 확인합니다.
- 학습 기록과 오류 기록의 각 검색 대상이 모두 검색되는지 확인합니다.
- 태그 하나와 날짜 기간을 각각 적용합니다.
- 검색어·태그·날짜·상태를 함께 적용해 모든 조건에 맞는 결과만 나오는지 확인합니다.
- 조건에 맞는 결과가 없을 때 빈 결과 안내가 나오는지 확인합니다.
- 다른 사용자의 기록이 검색 결과에 섞이지 않는지 확인합니다.
- 통합 검색이 임의로 추가되지 않았는지 확인합니다.

### 완료 조건

- 문서에서 정한 검색 대상과 모든 필터가 동작합니다.
- 여러 조건을 함께 사용할 수 있습니다.
- 결과 없음과 처리 실패를 구분합니다.
- 검색 결과는 항상 로그인한 사용자의 기록으로 제한됩니다.

## 13. Phase 9 — 대시보드

### 목표

로그인 후 사용자의 최근 활동과 남은 항목을 한 화면에서 확인하게 합니다.

### 진행 단계

#### 백엔드

1. 공부한 날짜가 최신인 학습 기록 5개를 제공합니다.
2. 미완료이면서 마감일이 가까운 할 일 5개를 제공합니다.
3. 마감일이 없는 할 일은 마감일이 있는 할 일 다음에 둡니다.
4. 최근 수정한 미해결 오류 5개를 제공합니다.
5. 모든 영역을 로그인한 사용자의 데이터로 제한합니다.

#### 프론트엔드

1. 최근 학습 기록 영역을 만듭니다.
2. 완료하지 않은 할 일 영역을 만듭니다.
3. 해결하지 못한 오류 영역을 만듭니다.
4. 각 영역에서 상세 내용 또는 해당 목록으로 이동하게 합니다.
5. 각 전체 목록으로 이동하는 버튼을 만듭니다.
6. 데이터 없음과 불러오기 실패를 구분해 보여줍니다.

### 확인 방법

- 각 종류를 6개 이상 만들어 5개만 올바른 순서로 나오는지 확인합니다.
- 할 일을 완료하면 미완료 영역에서 빠지는지 확인합니다.
- 오류를 해결됨으로 바꾸면 미해결 영역에서 빠지는지 확인합니다.
- 전체 목록 버튼과 각 항목 이동을 확인합니다.
- 다른 사용자의 데이터가 보이지 않는지 확인합니다.

### 완료 조건

- 세 영역이 각각 5개 이하로 올바른 순서로 나타납니다.
- 상태 변경이 대시보드에 반영됩니다.
- 이동 버튼과 실패 안내가 동작합니다.

## 14. Phase 10 — 반응형 화면과 공통 사용 경험

### 목표

완성된 기능을 컴퓨터와 휴대폰에서 편하게 사용할 수 있게 다듬고, 화면마다 다른 동작을 통일합니다.

### 진행 단계

1. 컴퓨터 화면에서 위쪽 메뉴와 넓은 목록 배치를 확인합니다.
2. 휴대폰 화면에서 메뉴 버튼으로 메뉴를 열고 닫게 합니다.
3. 입력칸, 버튼, 목록과 상세 내용이 화면 밖으로 벗어나지 않게 합니다.
4. 긴 오류 메시지와 코드 블록이 화면을 깨뜨리지 않게 합니다.
5. 작성·저장·수정·삭제 버튼의 위치와 표현을 통일합니다.
6. 모든 삭제 기능에 확인 절차가 있는지 점검합니다.
7. 성공, 잘못된 입력, 결과 없음, 불러오기 실패 안내를 통일합니다.
8. 빈 목록에서도 다음 행동을 이해할 수 있게 표시합니다.
9. 키보드만으로 주요 입력과 버튼을 사용할 수 있는지 확인합니다.

### 확인 방법

- 컴퓨터와 휴대폰 크기에서 전체 사용자 흐름을 실행합니다.
- 긴 제목, 긴 내용, 여러 태그와 코드 블록을 표시해 봅니다.
- 모든 화면의 메뉴, 입력칸과 버튼이 잘 보이고 눌리는지 확인합니다.
- 성공·실패·빈 결과와 삭제 확인 안내를 화면별로 확인합니다.

### 완료 조건

- 컴퓨터와 휴대폰에서 모든 주요 기능을 사용할 수 있습니다.
- 내용이나 버튼이 화면 밖으로 벗어나지 않습니다.
- 공통 동작과 안내 방식이 화면마다 일관됩니다.

## 15. Phase 11 — 전체 연결·보안·회귀 점검

### 목표

각 기능을 따로 확인하는 수준을 넘어 실제 사용 순서 전체가 안전하고 끊김 없이 동작하는지 검증합니다.

### 진행 단계

#### 전체 사용자 흐름

1. 새 계정 가입과 자동 로그인을 확인합니다.
2. 학습 기록, 할 일과 미해결 오류를 작성합니다.
3. 대시보드에 세 종류가 나타나는지 확인합니다.
4. 검색과 필터로 기록을 다시 찾습니다.
5. 할 일을 완료하고 오류를 해결됨으로 바꿉니다.
6. 기록을 수정하고 삭제합니다.
7. 로그아웃하고 다시 로그인해 저장 내용이 유지되는지 확인합니다.

#### 권한과 보안

1. 두 개 이상의 계정으로 서로의 목록이 섞이지 않는지 확인합니다.
2. 다른 사용자의 기록 주소로 직접 접근해도 내용을 볼 수 없는지 확인합니다.
3. 다른 사용자의 기록을 수정·삭제하거나 상태 변경할 수 없는지 확인합니다.
4. 로그인하지 않은 상태에서 개인 기능을 사용할 수 없는지 확인합니다.
5. 비밀번호 원문과 환경 비밀값이 노출되지 않는지 확인합니다.
6. 마크다운 내용이 다른 사용자의 화면이나 브라우저 동작을 위험하게 바꾸지 않도록 확인합니다.
7. 로그인 7일 유지와 로그아웃 후 상태 제거를 확인합니다.

#### 회귀 점검

1. SQLite3를 사용하는 각 Phase의 자동 확인을 전체 실행합니다.
2. `spec.md`의 전체 완료 확인표를 처음부터 끝까지 확인합니다.
3. 실패한 항목은 원인을 고친 뒤 관련 Phase와 전체 흐름을 다시 확인합니다.
4. 첫 번째 버전 제외 기능이 들어가지 않았는지 확인합니다.

### 완료 조건

- `spec.md`의 전체 완료 확인표가 모두 통과합니다.
- 정상 흐름, 잘못된 입력, 처리 실패와 권한 차단이 모두 확인되었습니다.
- 심각한 오류나 다른 사용자 정보 노출 문제가 남아 있지 않습니다.
- 새로고침과 재로그인 뒤에도 데이터가 유지됩니다.

## 16. Phase 12 — 배포와 첫 버전 공개

### 목표

완성된 BuildLog를 다른 컴퓨터와 휴대폰에서 접속할 수 있는 상태로 공개합니다.

### 진행 단계

1. 배포 시점에 프론트엔드와 백엔드를 제공하는 서비스의 무료 요금과 제한을 비교합니다.
2. 프론트엔드와 백엔드에 사용할 배포 서비스를 선택합니다.
3. 운영 환경에서 SQLite3 파일이 재배포 후에도 유지되는 저장 공간을 준비하고 데이터 구조를 적용합니다.
4. 운영용 비밀값과 서비스 주소를 환경 설정으로 등록합니다.
5. 프론트엔드와 백엔드를 배포하고 서로의 운영 주소를 연결합니다.
6. 운영 환경에서 안전한 연결을 사용하는지 확인합니다.
7. 새 계정으로 가입부터 로그아웃까지 전체 흐름을 다시 확인합니다.
8. 컴퓨터와 휴대폰의 서로 다른 인터넷 환경에서 접속해 봅니다.
9. 배포 방법, 필요한 환경 설정과 다시 배포하는 방법을 문서화합니다.
10. 배포된 서비스의 SQLite3 데이터가 재시작과 재배포 뒤에도 유지되는지 확인합니다.

### 확인 방법

- 개발에 사용한 컴퓨터가 아닌 다른 기기에서 사이트가 열리는지 확인합니다.
- 가입, 자동 로그인, 기록 저장, 검색, 상태 변경과 로그아웃을 실행합니다.
- 새로고침과 재로그인 뒤 데이터가 유지되는지 확인합니다.
- 다른 계정의 데이터가 노출되지 않는지 확인합니다.
- 비밀 설정값이 배포 결과나 저장소에 공개되지 않았는지 확인합니다.

### 완료 조건

- 인터넷에 연결된 컴퓨터와 휴대폰에서 BuildLog에 접속할 수 있습니다.
- 운영 환경에서 `spec.md`의 핵심 사용자 흐름이 정상 동작합니다.
- 비밀값과 사용자 데이터가 보호됩니다.
- 배포와 운영에 필요한 기본 문서가 준비되어 있습니다.
